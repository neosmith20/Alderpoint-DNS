# Project Status

Alderpoint DNS is a self-hosted DNS filtering appliance built on BIND (a
recursive, DNSSEC-validating backend that also serves RPZ-based filtering
policy and authoritative Local DNS records) and dnsdist (the client-facing
frontend, handling plain DNS, DoH, DoH3, DoT, and DoQ). A FastAPI web
console provides authenticated administration, and a lightweight analytics
collector aggregates query statistics from dnsdist and BIND without adding
any per-query overhead in the resolution path.

This document summarizes what is implemented, what is tested, and the
current state of the project. Alderpoint DNS is **beta software**; see
`docs/beta-readiness.md` for the external beta checklist and
`docs/known-limitations.md` for things that are not yet supported.

## Implemented areas

- [x] BIND recursive backend with DNSSEC, RPZ filtering, RNDC, statistics,
      and AppArmor confinement
- [x] dnsdist frontend: plain DNS, DoH, DoH3, DoT, DoQ, ACLs, rate limits,
      packet cache
- [x] Blocklist downloader/parser/compiler with safe, atomic RPZ deployment
      and rollback
- [x] Custom filtering rules (block/allow, exact rewrites, regex, AdGuard
      modifiers)
- [x] Local DNS (authoritative forward/reverse zones, PTR automation, split

- [x] Authenticated web interface
- [x] Aggregate and per-query analytics dashboard and query log
- [x] BIND cache management (sizing, TTL, prefetch, serve-stale, flush)
- [x] Upstream resolver management (plain DNS, DoT, DoH)
- [x] Encryption Settings for the client-facing listeners
- [x] Local backup and restore, including scheduled backups
- [x] Import and migration from CSV/hosts/zone files, Pi-hole, and AdGuard

- [x] Reviewed install/upgrade scripts, diagnostics bundle, and Debian

- [x] Full reboot and acceptance-suite verification

## DNS backend (BIND)

- Recursive resolution on a loopback listener, with DNSSEC validation
  (valid answers carry the AD flag; invalid answers return `SERVFAIL`).
- RPZ-based filtering policy is layered on top of recursion; an empty RPZ
  validates with `named-checkzone` and the full configuration validates
  with `named-checkconf` before every deploy.
- RNDC control and the JSON statistics channel are both restricted to
  loopback.
- AppArmor confinement is enabled with narrow path rules scoped to the
  application's own directories.
- The service is enabled and has been verified to survive stop/start and
  full host reboot cycles, including host resolution continuing to work
  correctly if the backend is briefly stopped and restarted.

## DNS frontend (dnsdist)

- Client-facing listeners bind to the host's public interfaces: UDP/TCP DNS
  on port 53, DoH/DoH3 on port 443 (path `/dns-query`), and DoT/DoQ on port
  853.
- dnsdist forwards to the BIND backend over loopback with PROXYv2 client
  address preservation, so BIND's access decisions and logs still see the
  real client address.
- The access control list defaults to RFC1918 private networks, loopback,
  and unique-local IPv6, with an environment-variable override available
  for deployments (e.g. behind a firewall/router) that need to allow a
  wider range.
- Rate limiting and a packet cache are configured for the frontend; a
  self-signed lab certificate is generated by default and can be replaced
  with a local CA-issued or uploaded certificate through Encryption
  Settings.
- Backend-outage behavior is tested: stopping the BIND backend correctly
  prevents frontend resolution, and restarting it restores service.

## Filtering

- A SQLite-backed catalog seeds a curated set of public blocklist sources
  with category assignments; sources can be added, edited, enabled/
  disabled, deleted, and updated individually or all at once.
- Supported list formats include plain domains, hosts-file rules, Adblock-
  style rules, exceptions, and IDN normalization; invalid/unsupported rules
  are reported rather than silently dropped.
- Custom allow rules always take precedence over both downloaded blocklists
  and custom block rules, and survive blocklist refreshes without ever
  modifying stored blocklist data.
- The custom filtering rule subsystem classifies exact and subdomain block/
  allow rules (`domain`/`||domain^`/`@@||domain^`), hosts-style exact
  rewrites (including IPv4/IPv6 addresses and multiple aliases per line),
  and `/REGEX/` rules. Regex rules are validated against a POSIX-ERE-
  compatible subset and rejected if they contain catastrophic-backtracking
  constructs (e.g. nested quantifiers like `(a+)+`) that could otherwise
  hang the "Test a domain" evaluation panel; no rule text is ever
  interpolated directly into generated dnsdist Lua. AdGuard `$` modifiers
  are handled explicitly: `$important` is honored as a priority marker,
  and unsupported modifiers (`$client`, `$dnstype`, `$ctag`, etc.) are kept
  visible and inactive with a specific reason rather than silently
  activating a broadened rule.
- Deployment uses a lock, staging, backup, atomic replacement, `rndc
  reload`, post-deploy functional DNS tests (ordinary/blocked/allowed), and
  rollback on any runtime failure. A failed source update preserves the
  last known-good downloaded copy.
- A configurable global Filter Update Interval (disabled, hourly, every 12
  hours, daily, every 3 days, or weekly) is backed by a systemd timer and a
  fixed, server-validated allowlist — no arbitrary intervals or shell input
  ever reach the scheduler.
- **Known limitation:** dnsdist's separate packet cache is not yet keyed
  per client/network. This is safe today because Alderpoint DNS applies one
  global filtering policy to every client, but it means the packet cache
  must be disabled or re-keyed before any future per-client/per-network
  policy feature is enabled at runtime — otherwise one client's answer
  could be served to another.

## Local DNS

- Uses `home.arpa` as the default internal domain and rejects `.local`.
- Stores A, AAAA, PTR, CNAME, TTL, comments, enabled state, automatic PTR
  linking, and client aliases in SQLite.
- Generated authoritative forward/reverse zones are separate from RPZ
  filtering policy. Records outside the default internal domain
  automatically create managed split-horizon forward zones, so custom
  FQDNs are served locally instead of being forwarded upstream.
- Deployment clears the relevant dnsdist packet-cache entries after
  activation, preventing stale "no such record" responses immediately
  after a record is added.
- The web UI provides simple and advanced record entry, alias management,
  CSV import/export, a hosts-file preview, and validation warnings for
  duplicates and conflicts.

## Web interface and authentication

- Runs as a dedicated non-root system account; the administration listener
  requires authentication and has no default administrator account.
- Passwords are hashed with Argon2; sessions are signed, `HttpOnly`, and
  `SameSite=Strict`; CSRF tokens protect mutating actions; login attempts
  are rate-limited by source IP.
- Privileged operations invoked from the web process are limited to a
  narrow, argument-constrained set of sudoers entries — there is no
  unrestricted shell access granted to the web service.
- Primary navigation is grouped into Dashboard, DNS, Security, Operations,
  and System sections, with active parent/child state, a collapsible
  desktop sidebar, and mobile/keyboard support. A global service-status
  indicator is present on every authenticated page.

## Analytics and dashboard

- The analytics collector runs as a restricted account, listening only on
  loopback. dnsdist's protobuf response logging feeds it with delayed
  delivery and bounded queuing; no SQLite writes occur in the live DNS
  path.
- Aggregate counters, latency, cache, and drop/health data are polled from
  dnsdist's loopback-only statistics API. Latency is stored in
  milliseconds everywhere, converted exactly once at the point it enters
  the system; per-query latency is computed from timestamps embedded in
  dnsdist's own protobuf payload, not from collector receive time, so a
  delayed or backlogged analytics queue cannot inflate reported latency.
  Negative latency from clock skew is clamped to zero, and implausible
  values are discarded rather than recorded.
- SQLite stores one-minute aggregate buckets plus recent detailed query
  events when detailed logging is enabled. Privacy modes support full,
  anonymized-client, and aggregate-only collection, with retention cleanup
  and database-size pruning.
- The dashboard includes range selection, metric cards, a time-series
  chart, top lists, protocol/response-code tables, recent activity, and
  per-upstream-resolver ranking (success/failure/timeout counts, latency,
  and historical snapshots) sourced from dnsdist's managed-backend
  counters.
- The Query Log supports search, filters, pagination, auto-refresh (via a
  partial-content endpoint that updates only the results, with
  session-persisted refresh state), and creating custom rules directly from
  a row.

## Upstream resolvers

- DNS Settings manages recursive upstream resolvers (plain DNS, DoT, DoH)
  without manual edits to BIND or dnsdist configuration, importing any
  existing BIND forwarders on first use.
- DoH requires bootstrap IPs for hostname-based upstreams; query strings
  and fragments in DoH URLs are rejected, and deployment messages sanitize
  URL-shaped values.
- Deployment renders generated includes for both BIND and dnsdist,
  validates configuration before applying it, restarts/reloads the
  relevant services, performs a real post-deploy lookup, records resolver
  health/latency, and restores the prior configuration on failure.
- The UI supports add, inline edit, enable/disable, reordering, and delete
  through async forms with immediate feedback.

## BIND cache management

BIND already performs recursive caching; this feature exposes and manages
that existing cache rather than adding a second one.

- Configurable maximum cache size (defaulting to roughly an eighth of total
  system RAM, bounded to a sane range), positive/negative min/max TTL, and
  prefetch/serve-stale tuning, validated to reject an oversized cache
  setting or inverted TTL bounds.
- Generated cache tuning lives in its own include file and is deployed
  through the same staged/backup/atomic/health-check/rollback path used
  elsewhere, running automatically as part of every configuration deploy.
- Cache flush (entire cache, one name, or one subtree) is applied through a
  narrowly scoped, argument-free privileged helper, with a recorded audit
  trail of completed, failed, and skipped flush actions.
- Cache statistics (hits, misses, hit percent, node count, memory use,
  eviction and expiry counts) are read from BIND's own statistics API. A
  dedicated Cache page exposes tuning, flush controls, and flush history.

## Encryption settings

- A dedicated Encryption Settings workflow manages dnsdist's DoH/DoH3/DoT/
  DoQ listeners. Plain UDP/TCP port 53 has no enable/disable control at
  all, so it can never be turned off from the UI.
- Certificate paths, the DoH path, and every protocol's port are
  configurable rather than hardcoded, with a one-time migration that
  parameterizes an existing installation while preserving its live console
  and webserver secrets.
- Deployment regenerates the relevant service configuration, validates it
  with the pending (not yet live) settings, restarts the frontend, waits
  for it to become active, and runs a real functional query per newly
  enabled protocol before declaring success; any failure restores the
  previous configuration and restarts back to the last-known-good state.
  A deploy where nothing actually changed is a fast no-op rather than an
  unnecessary restart.
- Supports self-signed certificate generation, a local CA issuing leaf
  certificates, certificate upload, and use of an existing certificate
  path. Cert/key match, SAN, validity window, and fingerprint are
  validated and displayed; private key contents are never rendered back to
  the browser.
- Ready-to-copy client connection strings and an Apple `.mobileconfig`
  profile for DoH/DoT are provided.
- **Known limitation:** DNSCrypt key/certificate generation via dnsdist's
  console functions does not reliably persist to disk under this
  deployment's process sandboxing. Rather than fabricate support, a failed
  DNSCrypt generation disables DNSCrypt for that deployment only (the
  stored setting is preserved and retried on the next deploy) without
  affecting the other protocols.

## Import and migration

- A dedicated Import and Migration page supports CSV (with auto-detected,
  admin-editable column mapping), XLSX, hosts files, a practical subset of
  BIND zone-file syntax, and Alderpoint DNS's own exported CSV/JSON
  formats.
- Upload parses into a preview without touching live state; every row is
  classified as valid, invalid (with a reason), duplicate, or conflicting
  against existing Local DNS records. The admin chooses skip/merge/replace
  per conflict, verified to do exactly what it claims and never silently
  overwrite an existing record.
- Apply takes an automatic pre-apply backup, tracks every inserted row, and
  supports rollback that deletes exactly those rows and leaves an audit
  trail.
- AdGuard Home migration accepts an uploaded configuration export or a
  direct read-only API connection (credentials used for one request and
  never stored), translating filter lists, custom rules, DNS rewrites, and
  client aliases into their Alderpoint DNS equivalents; anything that has
  no runtime equivalent is listed for manual review rather than silently
  dropped or imported incorrectly.
- Pi-hole text/list import handles adlists, allow/block lists, plain
  domain blocks, and hosts-style local DNS rewrites, with unsupported
  syntax shown as skipped.
- Migration reports strip credential-named fields and URL userinfo/query
  strings before they are ever stored or downloaded.
- Uploads are staged with sanitized filenames and a size limit so original
  sources remain available for troubleshooting without executing imported
  content.

## Backup and restore

- A dedicated Backup and Restore page produces versioned, checksummed
  archives and a preview-first, staged restore path with automatic
  rollback on failure.
- The SQLite database is always captured through SQLite's own online
  backup API rather than a raw file copy, so a concurrently writing web
  process or analytics collector can never produce a torn archive.
- Component selection controls which rows are stripped from the database
  copy before archiving (analytics history and authentication data are
  excluded by default) and, at restore time, which tables get merged into
  live SQLite — a narrow restore (e.g. only custom rules) never touches
  unrelated tables.
- Private key and credential material (TLS private keys, DNSCrypt keys,
  the session-signing secret, frontend API/webserver credentials) is
  excluded from every backup by default and requires an explicit,
  separately confirmed opt-in to include.
- Password-protected archives use industry-standard authenticated
  encryption with the password piped via stdin, never as a command-line
  argument, so it never appears in process listings.
- Restore always takes a full safety backup of current state before
  changing anything, stages and atomically replaces each selected
  filesystem component, merges selected database tables, validates
  configuration, restarts only the services actually touched, runs a real
  post-restore functional DNS test, and restores from the safety backup
  (reporting a clear rollback status) if anything fails.
- Scheduled backups run on a systemd timer with a configurable interval and
  retention pruning that keeps only the newest N archives.

## Replication

- One-way primary-to-replica replication uses token-based enrollment,
  mutual TLS, and generation hashes to detect drift between primary and
  replica state.
- A failed sync on the replica rolls back to its prior state rather than
  applying a partial update; a temporarily revoked replica certificate is
  denied by the primary's listener.
- Enrollment, drift detection, and revocation have all been verified in
  practice, in addition to unit test coverage.

## Installation, upgrade, diagnostics, and packaging

- `scripts/install.sh` supports fresh Debian-based server installs: checks
  OS/version, architecture, memory, and disk space; installs required
  packages; creates the dedicated system user/group; lays out the
  application, configuration, state, and log directories; creates a
  Python virtual environment; installs systemd units and sudoers policy;
  generates local secrets; initializes the database; deploys generated DNS
  configuration; enables services; and runs health checks. A dry-run mode
  with an alternate install root supports isolated validation.
- `scripts/upgrade.sh` detects current/target versions, checks disk space,
  creates a pre-upgrade backup and rollback snapshot, replaces application
  files while preserving persistent data, validates system state, runs
  migrations, restarts services in a controlled order, and restores the
  snapshot automatically on failure. It also supports dry-run testing
  against a fake root.
- A diagnostics command creates a sanitized tarball with version,
  OS/kernel/Python, service status, listeners, configuration validation
  results, schema object names, recent warnings, network/resource
  summaries, health-check results, and configuration metadata. It redacts
  passwords, API keys, session secrets, tokens, authorization headers,
  private-key PEM blocks, and resolver URL query strings; private DNS
  records and query contents are excluded by default.
- `VERSION`, `requirements.txt`, and `requirements-debian.txt` define the
  current beta version and dependency manifests.
- Debian packaging metadata and maintainer scripts preserve persistent data
  on a normal package removal; purge removes it only when explicitly
  requested.

## Testing and hardening

- A full acceptance suite covers the BIND backend, dnsdist frontend,
  blocklist deployment and failure-path rollback, web smoke tests, and
  backup/restore, and has been verified to pass across a full host
  reboot along with confirmation that services, listeners, DNS
  functionality, and feature persistence all survive intact.
- A hardening-review document covers authentication, authorization, CSRF,
  session cookies, input validation, upload handling, command execution,
  permissions, secret storage, logging/redaction, DNS recursion ACLs,
  public exposure, backup encryption, and replication auth/revocation, with
  an automated test verifying the required documentation and key hardening
  properties (recursion/cache ACL defaults, private-network ACL defaults,
  diagnostics redaction, secure-cookie support for HTTPS deployments).
- See `docs/testing.md` for the full list of test suites and what each one
  covers.

## Current status

Alderpoint DNS is in **beta**. Core DNS resolution, filtering, Local DNS,
the web interface, analytics, backup/restore, upstream resolver
management, encryption settings, import/migration, and replication are all
implemented and covered by automated tests, and have been exercised through
full-reboot verification. It is not yet a 1.0/production-readiness release:
expect continued hardening, expanded platform support, and possible
breaking changes to configuration or on-disk formats before a stable
release. See `docs/known-limitations.md` and `docs/beta-readiness.md` for
specifics.
